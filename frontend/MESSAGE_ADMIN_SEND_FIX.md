# Message Admin Send diagnosis and fix

## Exact observed cause

The actual database `Clean Room` Chore has no `family_id`, is assigned to its own creator, and that creator has the global Admin role. The assignee's real household is also owned by the assignee and has **zero other Admins**. The previous recipient lookup selected the creator, so the controller's self-recipient guard rejected Send before insertion.

A real HTTP request to the running backend reproduced:

```json
{"status":409,"response":{"message":"This chore has no separate responsible admin."}}
```

The endpoint, POST method, UUID payload, Bearer authentication, registered route, schema columns and database connection were working. The UI hid this specific recipient failure behind its generic error.

The original Chore still has no separate legitimate recipient. No assignment, account role or household data was changed to manufacture one. The user was asked which existing Admin should receive it, or whether to use a normal client’s Admin-assigned Chore. Until that relationship is clarified, this original self-owned Chore correctly returns `409 ADMIN_UNAVAILABLE`; it cannot safely be sent to an unrelated Admin.

## Changes

Backend: `backend/src/controllers/notificationController.js` only.

- Message-specific lookup prefers a separate assigning Admin, then a unique actual household owner. For legacy Chores without `family_id`, it uses the sender's real household memberships. A unique other household Admin is the final fallback. Ambiguous or absent recipients are rejected; self and arbitrary global Admins are never selected.
- Existing authenticated assignment and current household membership validation remain enforced.
- Specific safe response codes: `CHORE_NOT_ASSIGNED` (404), `ADMIN_UNAVAILABLE` (409).
- Development logs include the endpoint, status and safe validation/database code. Tokens, passwords and message text are not logged.
- Failed transactions attempt rollback without masking the original failure and release the connection.

Frontend:

- `src/services/notificationService.ts`: development diagnostics containing endpoint, POST method, status and safe API error response; uses the same centralized API client and token source.
- `src/components/notifications/PrivateChoreMessageForm.tsx`: distinguishes no Admin, lost assignment and expired session; retains failed input and clears it after a confirmed successful save. Existing appearance, counter, selector, Cancel/Send and duplicate-tap guard preserved.
- `src/i18n/privateMessageTranslations.ts`: the specific user-facing errors in English, Sinhala and Tamil.

Database/model changes: **none**. Uses existing `notifications.user_id` (recipient), `sender_id`, `chore_id`, `message`, `type`, `created_at` and `is_read`.

Tests updated: `backend/test/privateChoreMessages.postgres.test.js`, `frontend/scripts/test-private-chore-messages.cjs`.

New files: `backend/test/privateChoreMessageFailure.test.js`, `frontend/scripts/test-message-admin-request.cjs`, and this report.

## Request and successful response

`POST ${API_BASE_URL}/api/notifications/chore-messages` through the existing API client. Header: `Authorization: Bearer <current session token>`; the token is never logged. Base URL still comes from the existing `EXPO_PUBLIC_API_URL` configuration, with the existing fallback; no new hardcoded URL was added.

Example payload (replace the illustrative UUID with the selected actual database ID):

```json
{"chore_id":"11111111-1111-1111-1111-111111111111","message":"I can't do this chore at the assigned time."}
```

Successful response shape (201; ID/timestamp are generated by the database):

```json
{"message":"Message sent to Admin","notification":{"id":"<saved notification UUID>","created_at":"<actual database timestamp>"}}
```

The verified JWT subject supplies the sender. The server locks and validates the selected real Chore, derives the separate recipient, inserts the private notification and commits before returning success. It never trusts client-supplied sender/recipient IDs.

The existing Admin inbox retrieves it using `GET /api/notifications`, restricted to the signed-in recipient. Its existing card shows sender, Chore, current assigned date/time, original message and actual sent date/time. Reading uses `PATCH /api/notifications/:id/read`. Confirmed deletion uses `DELETE /api/notifications/:id`; a fresh login/reload confirms it remains gone. Other clients and unrelated Admins cannot list, read or delete the row.
