# Global Notification Settings and Reminder Time

1. **Existing architecture.** The existing notifications table and authenticated notification APIs provide a backend-generated in-app inbox with read/unread, refresh, time filters, counts and deletion. Existing personal_reminders and household_announcements support their existing CRUD routes. No second inbox or notification UI was created.
2. **Actual delivery capability.** This implementation delivers in-app notifications through the backend. No Expo local-notification, device token, push gateway or OS background-notification infrastructure exists in this project. No permissions or pretend device notifications were added.
3. **Preference architecture.** notification_settings already stores per-user category booleans and the stable reminder_time enum. Theme/language remain in the separate existing user_preferences table. Defaults remain reminders/completions/family ON, announcements OFF, reminder_time=10min; existing legacy fields are retained.
4. **Frontend modified files.** frontend/src/services/settingsService.ts; frontend/src/screens/home/Component04Screens.tsx; frontend/src/screens/home/ReminderTimeScreen.tsx; frontend/src/screens/admin/AdminSettingsScreen.tsx; frontend/src/i18n/clientTranslations.ts; frontend/src/i18n/adminTranslations.ts; frontend/src/i18n/crudTranslations.ts. Existing automatic-save interactions, four cards, separate Reminder Time screen, purple styling and navigation are retained. Retrieval requires real backend data; failed saves roll back, and duplicate taps are locked.
5. **Backend modified files.** backend/src/controllers/settingsController.js; backend/src/controllers/notificationController.js; backend/src/controllers/familyController.js; backend/src/routes/adminComponent04Routes.js; backend/src/routes/reminderRoutes.js (delivery comment); backend/src/config/db.js; backend/src/server.js; backend/test/settingsPersistence.test.js (rollback-only savepoint adaptation for controller transactions).
6. **Database/model change.** One additive notification_reminder_deliveries receipt table was added through the existing startup schema initialization. It contains user_id, delivery_key, chore_id, trigger_at, delivered_at and a unique user_id/delivery_key primary key. It is a delivery ledger, not a duplicate preference or notification table. It references users/chores with cascade cleanup and survives inbox deletion to prevent redelivery. No Chore column or existing preference field was added or removed. The running backend and integration tests initialized the schema successfully.
7. **APIs reused.** Existing GET/PUT /api/settings/notifications now support validated partial updates. Notification list/count, Chore, family, announcement, reminder, private-message and user-preference endpoints remain in use. No new public scheduling endpoint was introduced.
8. **Notification Settings persistence.** Each switch sends only its changed boolean. The backend applies an authenticated account-scoped transactional update, preserving every other field. The complete confirmed settings row is returned. Navigation/reload/login read the same database row rather than demo state.
9. **Reminder Time persistence.** Only reminder_time is written, using the existing enums 10min, 30min, 1hour and 1day. Its screen remains separate, single-selected and auto-saving. Translated display text is never stored as business data. Changing time does not reset category switches, Theme or Language.
10. **Chore Reminders ON/OFF.** The delivery worker checks the recipient's saved chore_reminders before generating automatic or explicit personal Chore reminders. OFF prevents new delivery while retaining assignments, Chores, Progress and delivered inbox history. ON restores eligibility for future pending assigned Chores. An elapsed trigger is caught up only while an automatic Chore's due time is still future. The retained legacy manual inbox-reminder creation API also rejects new creation when reminders are OFF; it remains an immediate authored-inbox API, not a device scheduling system.
11. **Chore Completions ON/OFF.** Existing completion-event generation already checks the creator/recipient's chore_completions preference. It remains immediate and unchanged: completing a Chore succeeds with notifications OFF, and old completion history is retained.
12. **Family Updates ON/OFF.** Existing join, add/update member and household-name operations now insert a family_update for other current household members whose family_updates is ON. Missing settings use the existing true default. Membership/name operations and their notifications commit together. Repeated joins and unchanged relationship updates do not produce repeat events. OFF affects the recipient's notification only.
13. **Announcements.** The existing publication API and screen still exist, despite previously removed entry-point buttons. They were not recreated or redesigned. The existing publish path already inserts announcements only for recipients with announcements=TRUE and deduplicates publication. The default remains false. Removed navigation buttons were not restored.
14. **Trigger calculation.** Automatic reminders use the current due timestamp minus 10/30/60/1440 minutes. Comparisons and stored receipt/inbox timestamps use absolute dates and PostgreSQL TIMESTAMPTZ; no timezone is hardcoded. Labels and displayed dates remain localized. Explicit My Reminders schedules retain their chosen remind_at rather than being rewritten by the automatic lead-time preference.
15. **Chore edits/rescheduling.** No per-Chore timer is physically queued. The worker reevaluates current database assignment, membership, status, due timestamp and selected lead time on every pass. Editing a due time immediately changes the eligible trigger; a title-only edit does not create a second occurrence.
16. **Deletion.** Deleted Chores or deleted personal reminder schedules cannot be selected for future delivery. Delivery receipts are cleaned by existing Chore/user foreign-key deletion; delivered inbox history otherwise remains intact according to existing inbox foreign-key behavior.
17. **Completion.** Only pending assigned Chores are eligible. Completing a Chore before the trigger suppresses its automatic and personal reminders without undoing completion or changing Progress.
18. **Deduplication.** Automatic keys identify user + Chore + exact due occurrence. Explicit personal keys identify user + saved reminder + chosen timestamp. Receipt insertion and inbox insertion commit in the same transaction. A unique receipt, account advisory lock and current Chore read locks coordinate concurrent workers/settings changes. Deleting the inbox row does not erase its receipt, so refresh/restart cannot recreate it. Changing lead time after delivery does not repeat the same due occurrence; a genuinely changed due occurrence may receive a new reminder.
19. **User specificity.** Preference updates and inbox queries use the authenticated req.userId. Delivery also checks current assignment, household membership where applicable, pending status and an active recipient account. Another account's settings are never used for the recipient.
20. **Ownership/security.** PUT rejects arbitrary user_id/unknown fields and invalid booleans/time enums. Existing authentication, role and ownership guards remain intact. Isolated real-database tests verify distinct accounts retain different settings and a spoofed target account ID is rejected.
21. **Message Admin.** Private client_chore_message generation/delivery is outside optional category gates. Real HTTP/database tests verify a Client message reaches the responsible Admin even when that Admin turns every optional category OFF. Existing read/delete ownership and unchanged Chore snapshots continue to pass.
22. **Chore CRUD.** Chore business/controller code was not modified by this task. Real tests create, assign, edit, reassign, complete and delete fixture Chores while exercising preferences. Reminder delivery only reads Chores; it does not modify their data.
23. **Theme/Language.** Existing global providers were unchanged. The Client/Admin appearance, preference-independence and language regressions still pass. New system notification templates translate known interface text while preserving captured Chore names/member/household data and private messages. Delivery explanatory text now accurately describes in-app capability.
24. **Existing interfaces.** No screen, dashboard, navigation, card layout, styling or authentication flow was redesigned. All/Today/This Week/Unread, refresh, read/delete and private messages retain their existing UI and regression coverage. No existing feature file was deleted.
25. **Delivery limits.** The API process must be running and connected to PostgreSQL. Its worker runs immediately at startup and every 30 seconds, and authenticated inbox/count requests also process eligible reminders. Actual arrival can be up to a polling interval after the calculated trigger; there is no promise of an exact device alarm. In-app inbox generation can occur with the client closed while the server is running, but there is no OS notification/banner or push delivery. If the server was offline, automatic reminders catch up while the Chore is still future, not after its due time. Existing legacy due_date_alerts/weekly_summary fields remain persisted; this task does not invent a weekly-summary service or separate due-date-alert category beyond the requested Chore reminder behavior.
